METHODOLOGY NOTE (read this before trusting the shapes below)
---------------------------------------------------------------
Task 4 originally called for filling a throwaway post by hand through the
Payload admin UI (`/admin/collections/posts/<id>`) and dumping its saved
JSON. That was not possible in this environment:

  1. `app/layout.tsx` (the real site's root layout) renders its own
     `<html>/<body>`. `app/(payload)/layout.tsx` nests Payload's own
     `<RootLayout>` (from `@payloadcms/next/layouts`) *inside* that — and
     `<RootLayout>` ALSO renders `<html>/<body>`. This is a fatal "cannot
     contain a nested <html>" React hydration error (confirmed via browser
     console) that blanks the entire `/admin/*` tree — visiting
     `/admin`, `/admin/login`, `/admin/collections/posts/1` all render only
     the marketing site's header/footer with an empty body.
  2. Independently, `app/(payload)/admin/importMap.js` is an unrun stub
     (`export const importMap = {}`), so even without bug (1), custom
     component paths (blocks, upload preview, etc.) would fail to resolve
     (`PayloadComponent not found in importMap`, seen in console).

  Both are pre-existing bugs in this repo, outside Task 4's scope to fix
  (fixing (1) requires restructuring the two layout files into separate,
  non-nested route groups; fixing (2) requires running Payload's
  `generate:importmap` and adding it as a project script). They should be
  reported/fixed separately before anyone relies on the live admin UI.

  Per the task brief's documented fallback ("construct the content field
  programmatically... based on the real TypeScript node types Payload/
  Lexical ship"), scripts/dump-sample-lexical.ts instead:
    1. Built a real headless Lexical editor via Payload's own
       `createHeadlessEditor` + `getEnabledNodes`, registering the actual
       node classes for every feature in play (Posts.content's real
       feature set, PLUS EXPERIMENTAL_TableFeature and the premade
       CodeBlock — added only inside the script, not in Posts.mts, purely
       to capture their real shapes; see "Table and code block are NOT
       currently usable in Posts.content" below).
    2. Fed it a hand-written JSON tree via `editor.parseEditorState()`,
       which calls each node class's real `importJSON()`.
    3. Re-serialized via `editor.getEditorState().toJSON()`, which calls
       each node's real `exportJSON()`.
  The shapes below are therefore genuine output of the installed
  lexical / @payloadcms/richtext-lexical node classes — including real
  version-migration side effects (see below) — not hand-typed guesses.
  The parts of the tree that Posts.content's live config actually supports
  (everything except `table` and the code `block`) were additionally
  round-tripped through a real `payload.create()` + `payload.findByID()`,
  so e.g. the upload node's `value` in the fixture is genuinely populated
  by Payload's relationship-population logic, not hand-assembled.

Table and code block are NOT currently usable in Posts.content
---------------------------------------------------------------
`collections/Posts.mts` configures `content`'s editor as:
  defaultFeatures + BlocksFeature({ blocks: [ToolLinkBlock] }) + UploadFeature(...)

`defaultEditorFeatures` (from `@payloadcms/richtext-lexical`) does NOT
include a table feature or any code-block feature. Concretely:
  - There is no native "code block" Lexical feature in this Payload
    version at all — only `InlineCodeFeature` for inline `` `code` ``
    formatting. A multi-line "code block" is a *premade Payload block*,
    `CodeBlock` (from `@payloadcms/richtext-lexical`, slug `'Code'` by
    default), meant to be added to `BlocksFeature({ blocks: [...] })`
    like any custom block.
  - Table support exists only as `EXPERIMENTAL_TableFeature` (note the
    "experimental" prefix in its own export name) and is not part of
    `defaultEditorFeatures`.

Calling `payload.create()` with a `table` node or a `block` node whose
`blockType` isn't registered fails Payload's own field-level validation
(this runs in the Local API too, not just the admin UI) with e.g.:
  "block node failed to validate: Block Code not found"

**If Task 5/6 need to store real code blocks or tables in post content,
Posts.mts's `content` editor features must first be extended with
`CodeBlock()` (added to `BlocksFeature`'s `blocks` array) and
`EXPERIMENTAL_TableFeature()`.** That is a real, small, one-line-per-feature
change to `collections/Posts.mts` — not done here since it's outside this
task's scope (fixture-capture only, no schema changes) — but it is a
concrete unblocking action for whoever picks up Task 5/6 if the plan needs
those two node types to round-trip through Payload itself.

NODE SHAPES (exact keys observed in sample-lexical.json)
===========================================================================

## text node — `type: 'text'`
```
{ "type": "text", "version": 1, "detail": 0, "mode": "normal", "style": "", "format": <number>, "text": "..." }
```
- `format` is a NUMBER bitmask, not a string. Observed values: `0` = no
  formatting, `1` = bold (IS_BOLD), `2` = italic (IS_ITALIC), `3` = bold +
  italic (bitwise OR: 1|2). Other bits (not exercised in the fixture but
  standard Lexical constants): underline=8, strikethrough=4, code=16,
  subscript=32, superscript=64, highlight=128.

## paragraph node — `type: 'paragraph'`
```
{ "type": "paragraph", "version": 1, "format": "", "indent": 0, "direction": "ltr",
  "textFormat": 0, "textStyle": "", "children": [...] }
```
Note `format` on the paragraph/root/heading/list/etc (element-level) is a
STRING (usually `""`, or an alignment keyword like `"center"`), unlike the
text node's numeric `format`. Do not confuse the two.

## heading node — `type: 'heading'`
```
{ "type": "heading", "version": 1, "tag": "h2", "format": "", "indent": 0,
  "direction": "ltr", "children": [...] }
```
- Heading level lives in `tag` (`"h1"`..`"h6"`), not in `type`.

## list node — `type: 'list'`
```
{ "type": "list", "version": 1, "listType": "bullet"|"number", "start": 1,
  "tag": "ul"|"ol", "format": "", "indent": 0, "direction": "ltr", "children": [...] }
```
## list item node — `type: 'listitem'`
```
{ "type": "listitem", "version": 1, "value": <1-based index>, "format": "",
  "indent": 0, "direction": "ltr", "children": [...] }
```
(A checklist item would additionally carry `"checked": boolean` — not
exercised in the fixture since Posts.content doesn't need it, but
`ChecklistFeature` is in `defaultEditorFeatures`.)

## link node — `type: 'link'`
```
{ "type": "link", "version": 3, "format": "", "indent": 0, "direction": "ltr",
  "fields": { "linkType": "custom", "url": "https://...", "newTab": true },
  "children": [...] }
```
- URL lives at `fields.url` (only present when `fields.linkType ===
  'custom'`; `exportJSON()` actively `delete`s `url` when `linkType ===
  'internal'`, and `delete`s `fields.doc` when `linkType === 'custom'` — the
  two are mutually exclusive on the wire, never both present).
- New-tab flag is `fields.newTab: boolean`.
- Internal Payload-document links carry `fields.doc = { relationTo,
  value }` instead of `fields.url`. This repo's Posts.mts does NOT use
  Payload's internal-doc link type for `/tools/*` paths (tool pages aren't
  Payload documents) — a link to `/tools/password-generator` is just
  `fields.linkType: 'custom'`, `fields.url: '/tools/password-generator'`.
- **Version migration observed live**: feeding a `version: 2` link node
  with no `id` field caused `LinkNode.importJSON()` to auto-generate an
  `id` (a `bson-objectid` hex string) and bump `version` to `3`. A
  version-1 link node additionally had `fields.doc.value` unwrapped from a
  populated object down to a bare id before the v2→v3 step.

## block node (custom Lexical blocks, e.g. ToolLinkBlock, CodeBlock) — `type: 'block'`
```
{ "type": "block", "version": 2, "format": "",
  "fields": { "blockType": "<block slug>", "id": "<objectid hex>", ...blockOwnFields } }
```
- The block's Payload-config slug (e.g. `'toolLink'`, `'Code'`) is
  `fields.blockType` — NOT a top-level `blockType` key, and NOT
  `fields.data.blockType`.
- The block's own configured fields are flattened directly into `fields`
  alongside `blockType`/`id`/`blockName` (e.g. ToolLinkBlock's `toolPath`
  and `subtitle` appear as `fields.toolPath`, `fields.subtitle`).
- `fields.id` is auto-generated (`bson-objectid` hex string) if omitted.
- **Version migration observed live**: a `version: 1` block node has its
  fields wrapped one level deeper, under `fields.data` (i.e.
  `{ fields: { data: { blockType, ...ownFields } } }`); `importJSON()`
  unwraps `fields.data` up to `fields` directly and bumps `version` to `2`.
  Concretely for the CodeBlock example in the fixture: feeding
  `fields: { data: { blockType: 'Code', language: 'javascript', code:
  '...' } }` at version 1 produced
  `fields: { blockType: 'Code', language: 'javascript', code: '...', id:
  '...' }` at version 2.
- CodeBlock specifically (slug defaults to `'Code'`): raw code text is
  stored as a single plain string at `fields.code` (a Payload `code`-type
  field — NOT split into per-line or per-token Lexical text nodes), and
  the language is `fields.language` (a Payload `select` field, e.g.
  `"javascript"`).

## upload node (image via the Upload feature) — `type: 'upload'`
```
{ "type": "upload", "version": 3, "format": "",
  "id": "<objectid hex>", "relationTo": "media", "value": <id | populated doc>,
  "fields": null }
```
- All of `relationTo`, `value`, `fields`, `id` are flattened directly onto
  the node (there is no nested `data` wrapper in the wire format, even
  though internally the class stores them under `__data` / constructs via
  `{ data: {...} }} — that's a Lexical-node-instance implementation detail,
  not the serialized JSON shape).
- `value` is the raw media id when read straight from the DB, or the
  fully populated media document when read through Payload's normal
  population (e.g. `payload.findByID()` at default depth, or the REST API)
  — confirmed in the fixture: `value` is the complete `media` doc object
  (`id`, `alt`, `url`, `filename`, `mimeType`, `filesize`, `width`,
  `height`, `focalX`, `focalY`, `updatedAt`, `createdAt`).
- `fields` holds the upload feature's extra per-instance sub-fields
  (configured in Posts.mts as `UploadFeature({ collections: { media:
  { fields: [] } } })` — empty, hence `fields: null` in the fixture).
- **Version migration observed live**: a `version: 2` upload node with no
  `id` was auto-upgraded to `version: 3` with a generated `id` (same
  `bson-objectid` pattern as link/block nodes). A version-1 node with a
  populated `value.id` object would additionally get `value` collapsed
  down to the bare id first.

## table / tablerow / tablecell nodes (from `@lexical/table`, via
## `EXPERIMENTAL_TableFeature` — NOT currently enabled on Posts.content)
```
table:     { "type": "table", "version": 1, "format": "", "indent": 0, "direction": "ltr", "children": [tablerow, ...] }
tablerow:  { "type": "tablerow", "version": 1, "format": "", "indent": 0, "direction": "ltr", "children": [tablecell, ...] }
tablecell: { "type": "tablecell", "version": 1, "format": "", "indent": 0, "direction": "ltr",
             "headerState": <number>, "colSpan": 1, "rowSpan": 1, "backgroundColor": null,
             "children": [paragraph, ...] }
```
- These are the standard, un-modified `@lexical/table` node classes — no
  Payload-specific wrapping.
- A table cell's content is itself a normal element-node tree (in the
  fixture, one `paragraph` per cell containing `text` children) — a cell
  is NOT a plain string.
- `headerState` is a number from `TableCellHeaderStates` (`NO_STATUS: 0`,
  `ROW: 1`, `COLUMN: 2`, `BOTH: 3`). The fixture's first row (used as a
  header row) has `headerState: 1` on both its cells; the second (body)
  row has `headerState: 0`.
- `TableNode` can also carry `colWidths`, `rowStriping`,
  `frozenColumnCount`, `frozenRowCount` — not present in the fixture
  (defaults omitted by `exportJSON()` when unset).

## horizontal rule node — `type: 'horizontalrule'`
```
{ "type": "horizontalrule", "version": 1 }
```
- No `children`, no `format`/`indent`/`direction` — the minimal possible
  node shape (a `DecoratorNode` with no configurable state).

## root node — `type: 'root'`
```
{ "type": "root", "version": 1, "format": "", "indent": 0, "direction": "ltr", "children": [...] }
```
